# POPO Stage 5C.1 — 회원별 사주 정보 보관함

기준 날짜: 2026-11-05. 기존의 승인된 메인/440px 모바일 화면, Sabrina 로고, Pretendard 본문 및 카카오 로그인 설정은 바꾸지 않는다.

## 구현 범위

마이페이지의 `+ 내 사주 입력하기` → 출생정보 입력 → `popo_profiles` 저장 → 목록 재조회 → 수정/삭제. `저장된 사주 관리하기`는 같은 보관함 목록을 연다. 새로고침 후 다시 여는 경우 실제 DB에서 다시 조회한다. 현재 단계에서 실제 만세력·대운·세운·AI 결과를 계산하거나 생성하지 않는다.

입력: 이름/별명, 본인·연인·가족·친구·기타 직접입력, 양력/음력, 윤달, 생년월일, 출생 시간 또는 모름, 성별 또는 모름, 기존 지역 선택값. 지역 목록의 순서와 값은 기존 화면을 재사용한다. 추가 행정구역 사실을 검증했다는 의미가 아니다.

## 기존 SQL과 계약

기존 Stage 5A-R `popo_profiles` 컬럼을 사용하며 SQL이나 RLS를 수정하지 않는다. `user_id`는 폼이 아니라 `auth.getUser()`의 확인된 사용자 ID에서 생성하고, 읽기/수정/삭제는 `user_id` 및 필요한 `id`로 필터링한다. 최종 권한 판단은 실제 Supabase RLS에 의존한다. `is_anonymous`인 Supabase 계정은 회원 등록 기능에 사용할 수 없도록 차단한다.

프로필 저장을 위한 `id`는 브라우저의 `crypto.randomUUID()`로 한 번 생성한다. 네트워크 응답이 유실된 INSERT를 재시도하면 같은 ID를 재사용하고, 중복 키가 나왔을 때 소유자 필터와 동일한 값인지 확인한다. 기존 사주/궁합 보고서 테이블에 클라이언트가 쓰는 경로는 없다.

## 개인정보와 오류

출생정보는 이 모듈에서 별도의 localStorage/sessionStorage에 저장하지 않는다. 기존 카카오 인증 SDK의 세션 보관 동작은 변경하지 않는다. 브라우저 로그에 원본 출생정보나 토큰을 출력하지 않는다. 사용자 이름은 `textContent`로 그리며 HTML 삽입을 사용하지 않는다.

로그아웃/다른 계정으로 전환되면 열린 보관함과 입력 정보를 정리한다. 계정 확인 중 전환이 일어나면 이전 폼을 새 계정에 INSERT하지 않는다. 저장/삭제가 이미 서버로 전송된 뒤에는 취소가 DB 작업 철회를 보장하지 않으므로, 화면에는 늦은 응답만 차단한다.

저장 실패 시 입력을 보존하고 성공 문구를 보여주지 않는다. 저장 자체는 성공했으나 목록 갱신만 실패했다면 두 상태를 구분해 안내한다. 삭제에는 연결된 보고서가 함께 삭제될 수 있다는 확인을 받는다.

## 알려진 범위 제한

- 신규 등록 5명 제한은 UI 정책이며 DB 차원의 강제 한도가 아니다. 이미 더 많은 레코드가 있는 경우 숨기지 않고 20개씩 페이지 조회한다.
- 날짜는 기존 DB의 PostgreSQL `date` 형식이다. 음력 날짜의 양력 변환/윤달 정확성 검증은 하지 않는다. 특히 음력 2월 30일은 기존 스키마에서 표현할 수 없어 명시적으로 거절한다. 다른 날짜로 바꾸어 저장하도록 유도하지 않는다. 향후 날짜 저장 스키마 또는 정규화 설계가 필요하다.
- 사주 결과와 프로필 변경 버전 연결은 다음 단계다. 저장된 결과가 생기면 수정 시 재계산/버전 식별이 필요하다.
- Supabase 실사용 두 계정의 교차 접근 차단 검증은 별도로 수행해야 한다. 모의 브라우저 테스트로 RLS 안전성을 인증하지 않는다.
